API 서버의 CPU가 하루에 몇 번씩 80%까지 튀었습니다. 원인은 트래픽이 아니라 요청 한 건이었습니다. 우리 앱이 보내는 요청이 아니라 외부 사용자가 직접 만든 커스텀 쿼리였고, 그 쿼리는 DB 쿼리를 약 4,900번 일으키고 있었습니다. 두 번의 수정으로 8.6초를 0.36초로 줄인 과정을 정리합니다.

## 증상: 평균은 멀쩡한데 최대치만 튄다

ECS 서비스 모니터링에서 CPU 최대치가 평소 10% 안팎이다가 순간적으로 80% 가까이 올라갔습니다. 메모리도 같은 시각에 10%대에서 25%까지 튀었습니다. 평균값은 거의 움직이지 않았고, 1분 정도 솟았다가 바로 내려오는 모양이었습니다.

서버는 Node.js(Express + Apollo Server 2), type-graphql, TypeORM 구성이고 태스크 한 개로 돌고 있습니다. 서버 안에는 크론이나 스케줄러가 없습니다. 그렇다면 스파이크는 밖에서 들어온 요청이 만든 것이어야 했습니다.

## 추적 1: 요청 로그에서 범인 찾기

우리 서버는 성공한 GraphQL 요청마다 오퍼레이션 이름, 소요 시간, 변수, 유저를 DB 테이블에 남깁니다. 500ms를 넘긴 요청은 응답 본문도 일부 저장합니다. APM이 없어도 이 테이블 하나로 꽤 많은 것을 알 수 있었습니다.

스파이크 시각 전후를 소요 시간 순으로 조회했습니다.

```sql
SELECT creationTime, operationName, elapsed, userId
FROM successLog
WHERE creationTime BETWEEN '...' AND '...'
ORDER BY elapsed DESC
LIMIT 50;
```

| 시각 | 오퍼레이션 | 소요 시간 |
| --- | --- | --- |
| 14:36 | `GetIotDetail` | 7,921ms |
| 14:39 | `GetIotDetail` | 8,450ms |
| 14:50 | `GetIotDetail` | 8,770ms |
| 15:11 | `GetIotDetail` | 8,660ms |

네 건 모두 같은 유저, 같은 기기였고 그래프의 스파이크 시각과 일치했습니다. 분 단위로 집계해 보니 해당 분의 전체 요청 수는 2~4건이었습니다. 요청이 몰린 게 아니라 한 건이 무거웠던 것입니다.

## 추적 2: 앱이 보낸 요청이 아니었다

이상한 점이 있었습니다. `getIotDetail`은 우리 앱도 쓰는 쿼리입니다. 기기 상태를 조회하는 용도로 만들었고, 앱에서는 느릴 이유가 없습니다. 그런데 느린 호출은 모두 한 유저에게서 나왔습니다. 그 유저가 보낸 오퍼레이션을 집계해 보니 그림이 분명해졌습니다.

| 오퍼레이션 | 횟수 | 의미 |
| --- | --- | --- |
| 배변 기록 조회 | 5,979 | 약 80초 간격으로 5일 넘게 폴링 |
| `Login` | 44 | 앱의 자동 로그인이 아닌 직접 로그인 |
| `GetIotDetail` | 43 | 문제의 쿼리 |
| `X` | 6 | 손으로 쓴 실험용 쿼리 |

로그인한 뒤 실험용 쿼리를 몇 번 보내고, 직접 조합한 쿼리를 주기적으로 호출하기 시작했습니다. 앱이 아니라 외부 사용자가 만든 스크립트였습니다.

본인 계정으로 본인 기기의 데이터를 조회한 것이라 권한 문제는 없습니다. 자기 기기의 데이터를 자기 방식대로 쓰고 싶었던 것으로 보입니다.

## AI 시대의 IoT 서버

이런 호출은 앞으로 더 늘어날 것으로 봅니다. 예전에는 앱의 통신을 분석하고 호출 스크립트를 짜는 일에 꽤 많은 시간과 지식이 필요했습니다. 지금은 AI 도구에 맡기면 금방 끝납니다. 내 기기의 데이터를 홈 자동화에 연결하거나 나만의 대시보드로 만들고 싶은 사용자에게 진입 장벽이 사실상 사라졌습니다.

특히 IoT 서비스는 "내 기기, 내 데이터"라는 동기가 뚜렷해서, 공식 앱 밖에서 서버를 입맛대로 호출하려는 수요가 큽니다. 서버 입장에서는 전제가 하나 바뀝니다.

> "클라이언트는 우리 앱뿐이다"라는 가정은 더 이상 성립하지 않습니다.

앱 밖에서 서버를 직접 호출하는 사례는 이전에도 있었습니다. 다만 그때는 앱이 쓰던 쿼리를 그대로 가져다 보내는 수준이었습니다. 호출하는 주체만 달랐을 뿐, 서버가 받는 쿼리는 이미 테스트되고 성능이 확인된 것이었습니다.

이번에는 달랐습니다. 원하는 필드를 골라 쿼리를 마음대로 조합해서 보냈습니다. 앱이 한 번도 보낸 적 없는 쿼리이니 테스트된 적도, 성능을 확인한 적도 없습니다. 이제는 그런 쿼리가 언제든 들어올 수 있다고 보고 서버를 설계해야 합니다.

## 추적 3: 왜 8초인가

리졸버 코드는 가벼웠습니다. 기기 한 건을 조인 몇 개와 함께 읽고, `Iot` 엔티티를 그대로 반환합니다.

```ts
@Query(() => Iot)
async getIotDetail(@Arg('data') data: IotIdArgs) {
  const iot = await this.iotRepo
    .createQueryBuilder('iot')
    .leftJoinAndSelect('iot.pet', 'pet')
    // ...
    .where('iot.id = :iotId', { iotId: data.iotId })
    .getOne();
  return iot;
}
```

실마리는 저장된 응답 본문에 있었습니다.

```text
{"getIotDetail":{"poopLogs":[
  {"id":..., "newCatWeight":5745, "duration":50, "cat":null},
  {"id":..., "newCatWeight":3214, "duration":61, "cat":{"nickname":"..."}},
  ...
```

응답에 배변 기록 목록이 통째로 들어 있었고, 기록마다 고양이 정보가 붙어 있었습니다.

### lazy relation이 GraphQL 필드가 되면

엔티티에는 이렇게 선언돼 있습니다.

```ts
// Iot
@Field(() => [PoopLog])
@OneToMany(() => PoopLog, (poopLog) => poopLog.iot)
poopLogs: Promise<PoopLog[]>;

// PoopLog
@Field(() => Cat, { nullable: true })
@ManyToOne(() => Cat, (cat) => cat.poopLogs)
cat: Promise<Cat | null>;
```

TypeORM에서 relation 타입을 `Promise`로 선언하면 lazy relation이 됩니다. 속성에 처음 접근하는 순간 쿼리가 나갑니다. 여기에 `@Field`를 붙이면 다음 등식이 성립합니다.

> 클라이언트가 쿼리에서 필드를 선택한다 = 서버가 그 속성을 읽는다 = DB 쿼리가 나간다

리졸버를 따로 쓰지 않아도 연관 데이터가 딸려 나오니 편합니다. 대신 `getIotDetail`처럼 엔티티를 그대로 반환하는 쿼리는 그 엔티티에 달린 relation을 전부 열어 주게 됩니다. 상태 조회용으로 만든 쿼리로 배변 기록까지 가져갈 수 있었던 이유입니다. 그리고 어떤 쿼리가 나갈지를 서버 코드가 아니라 클라이언트가 보낸 쿼리 모양이 결정합니다. 클라이언트가 우리 앱뿐일 때는 드러나지 않던 문제입니다.

외부 사용자가 만든 쿼리는 이런 모양이었습니다.

```graphql
query GetIotDetail($data: IotIdArgs!) {
  getIotDetail(data: $data) {
    poopLogs {
      id
      newCatWeight
      duration
      cat { nickname }
    }
  }
}
```

이 쿼리가 서버에서 일으킨 일은 두 가지입니다.

- **전체 조회.** lazy 로딩에는 조건이나 `LIMIT`을 넣을 자리가 없습니다. 엔티티의 필드로 가져가는 한 날짜로 범위를 제한할 방법이 없어서, 요청하면 항상 모든 기록이 나갑니다. 이 기기에 1년간 쌓인 기록 4,910건을 전부 읽었습니다.
- **N+1.** lazy 로딩은 객체 하나 단위로 일어납니다. 기록 4,910건 각각에서 `cat`을 읽으면서 쿼리가 4,910번 더 나갔습니다.

```sql
SELECT ... FROM poopLog WHERE iotId = ?      -- 1번, 4,910행
SELECT ... FROM cat ... WHERE poopLog.id = ? -- 4,910번
```

Node는 단일 스레드라, 이 요청이 처리되는 8초 동안 들어온 다른 유저의 요청도 함께 느려졌습니다.

호출한 사용자는 서버가 허용하는 쿼리를 보냈을 뿐입니다. 문제는 그런 쿼리가 가능하도록 열어 둔 서버에 있었습니다.

## 해결 1: 조인 한 번으로 미리 채우기

lazy relation은 값이 이미 채워져 있으면 쿼리를 날리지 않습니다. 요청에 `poopLogs`가 있을 때만, 기록과 고양이를 조인한 쿼리 한 번의 결과를 미리 넣어 줬습니다.

```ts
async getIotDetail(@Arg('data') data: IotIdArgs, @Info() info: GraphQLResolveInfo) {
  const iot = /* 기존 조회 */;

  const isPoopLogsRequested = info.fieldNodes.some((fieldNode) =>
    fieldNode.selectionSet?.selections.some(
      (selection) => selection.kind === 'Field' && selection.name.value === 'poopLogs',
    ),
  );

  if (isPoopLogsRequested) {
    iot.poopLogs = this.poopLogRepo
      .createQueryBuilder('poopLog')
      .leftJoinAndSelect('poopLog.cat', 'cat')
      .where('poopLog.iotId = :iotId', { iotId: iot.id })
      .orderBy('poopLog.id', 'ASC')
      .getMany();
  }

  return iot;
}
```

TypeORM(0.2.x) 소스에서 두 가지를 확인하고 썼습니다. lazy 속성에 `Promise`를 대입하면 그 `Promise`가 그대로 쓰입니다. 그리고 조인 결과가 없는 행은 `null`로 채워져 "로드 완료"로 취급되므로 추가 쿼리가 나가지 않습니다.

쿼리 수는 약 4,900번에서 1번으로 줄었습니다. 수백 ms로 내려갈 것이라 기대했는데, 결과는 달랐습니다.

**약 8,600ms → 약 3,760ms**

5초가 줄었지만 3.7초가 남았습니다.

## 해결 2: 한 달치만 내려주기

남은 3.7초를 다시 추적했습니다. 같은 조건의 SQL을 DB에서 직접 실행하면 금방 끝났습니다. 그 사용자가 쿼리를 바꿨는지도 확인했지만, 저장된 응답은 수정 전후가 똑같았습니다.

남은 것은 서버가 하는 일이었습니다. 4,910건을 엔티티 객체로 만들고, 필드 약 5만 개를 하나씩 처리하고, JSON으로 직렬화하는 비용입니다. 쿼리 수를 줄여도 이 비용은 건수에 비례해서 그대로 남습니다.

그래서 건수 자체를 줄였습니다.

```ts
const oneMonthAgo = moment().subtract(1, 'month').toDate();

iot.poopLogs = this.poopLogRepo
  .createQueryBuilder('poopLog')
  .leftJoinAndSelect('poopLog.cat', 'cat')
  .where('poopLog.iotId = :iotId', { iotId: iot.id })
  .andWhere('poopLog.creationTime >= :oneMonthAgo', { oneMonthAgo })
  .orderBy('poopLog.id', 'ASC')
  .getMany();
```

| 단계 | 평균 소요 시간 |
| --- | --- |
| 수정 전 | 약 8,600ms |
| N+1 제거 후 | 약 3,760ms |
| 한 달 제한 후 | 약 360ms |

건수가 약 12분의 1로 줄자 시간도 약 10분의 1이 됐습니다. 남은 시간이 건수에 비례하는 처리 비용이었다는 것이 수치로 확인됐습니다. 처음과 비교하면 약 24분의 1이고, 기록이 더 쌓여도 느려지지 않습니다.

응답이 바뀌는 수정이라 고민이 있었습니다. 다만 앱은 이 쿼리를 상태 조회에만 쓰고 `poopLogs`를 가져가지 않으므로 앱 화면에는 영향이 없습니다.

## 남은 숙제

이번 수정은 경로 하나를 막은 것입니다. 앱 밖에서 오는 호출이 늘어난다는 전제로, 아래 작업을 이어서 진행합니다.

- **쿼리 깊이 제한.** 양방향 relation을 타고 끝없이 파고드는 쿼리를 막습니다. 다만 이번 쿼리는 깊이가 3이라 깊이 제한만으로는 걸러지지 않습니다.
- **쿼리 복잡도 제한.** 필드별 비용을 합산해 한도를 넘는 쿼리를 실행 전에 거부합니다. 처음에는 거부 없이 점수만 기록해 정상 쿼리의 분포부터 봅니다.
- **스키마 정리.** 계속 쌓이는 로그성 relation은 GraphQL 필드에서 빼고, 필요한 것은 페이지네이션이 있는 전용 쿼리로 제공합니다.

## 배운 점

- 평균이 아니라 최대치가 튄다면 "무거운 요청 한 건"을 의심합니다. 요청 수가 아니라 요청별 소요 시간을 봐야 합니다.
- 클라이언트는 우리 앱만이 아니고, 쿼리도 앱의 것만이 아닙니다. 예전에는 앱의 쿼리를 그대로 따라 보내는 정도였지만, 이제는 마음대로 조합한 쿼리가 들어옵니다.
- 느린 요청의 응답 본문을 남겨 둔 것이 결정적이었습니다. 쿼리 본문이 없어도 응답 모양만으로 무엇을 요청했는지 알 수 있었습니다.
- lazy relation에 `@Field`를 붙이는 것은 쿼리 권한을 클라이언트에 넘기는 일입니다. 단건 관계에는 편리하지만, 계속 쌓이는 목록에는 쓰지 않는 편이 안전합니다.
- 쿼리 수를 줄여도, 수천 건을 통째로 내려주는 비용은 남습니다. N+1을 없앤 뒤에도 3.7초가 남았고, 건수를 제한하고서야 해결됐습니다.
- N+1은 데이터가 쌓여야 드러납니다. 기록이 수십 건일 때는 아무도 눈치채지 못합니다.
