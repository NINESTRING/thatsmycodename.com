## 들어가며

RDS는 프라이빗 서브넷에 두는 것이 기본입니다. 문제는 그다음입니다. 개발자는 로컬에서 쿼리를 확인해야 하고, 마이그레이션을 검증해야 하고, 장애 때는 데이터를 직접 봐야 합니다.

저도 이 문제를 여러 방식으로 풀어 왔습니다. 처음에는 RDS 서브넷의 라우팅 테이블에서 회사 IP 하나만 인터넷 게이트웨이로 연결해, 회사 망에서만 RDS에 접속할 수 있게 했습니다. 나중에는 EC2 한 대에 phpMyAdmin을 설치해 그 화면으로 데이터를 봤습니다. 다른 회사에서는 Site-to-Site VPN으로 회사 망에서 AWS 프라이빗 IP에 바로 접속했는데, 열리는 범위가 너무 넓어 보안 면에서 좋아 보이지 않았습니다. 그러다 만난 것이 프록시를 거쳐 연결하는 방식입니다. 팀에 합류했을 때 이미 이렇게 쓰고 있었고, 지금까지 겪은 방법 중 가장 낫다고 생각해 글로 소개합니다.

이 글은 프라이빗 RDS에 접근하는 방법들을 비교하고, 우리 팀이 쓰는 `kubectl port-forward` + socat 프록시 구성과 그 한계를 정리합니다.

방법을 평가할 때 쓴 기준은 다섯 가지입니다.

- **인바운드 노출**: 인터넷이나 사내망에 열어야 하는 포트가 있는가
- **자격증명 관리**: SSH 키나 고정 비밀번호를 배포하고 회수해야 하는가
- **접근 통제와 감사**: 누가 접근할 수 있는지 중앙에서 관리되고, 기록이 남는가
- **비용과 운영 부담**: 새로 만들고 관리해야 하는 리소스가 무엇인가
- **사용성**: 개발자가 명령 한 줄로 쓸 수 있는가

## 선택지 비교

| 방법 | 추가 리소스 | 인바운드 노출 | 접근 통제 | 비용 구조 |
| --- | --- | --- | --- | --- |
| Bastion + SSH 터널 | 퍼블릭 서브넷의 EC2 | 22번 포트 | SSH 키, 보안 그룹 | EC2 상시 가동 |
| SSM 포트포워딩 | 프라이빗 서브넷의 중계 EC2 | 없음 | IAM | 소형 EC2, NAT가 없으면 VPC 엔드포인트 |
| EC2 Instance Connect Endpoint | 엔드포인트와 중계 EC2 | 없음 | IAM | 엔드포인트는 무료, EC2 비용 |
| kubectl port-forward | 클러스터 안의 프록시 파드 | 없음 | 쿠버네티스 RBAC | 기존 클러스터에 파드만 추가 |
| Client VPN | VPN 엔드포인트 | VPN 엔드포인트 | 인가 규칙, 보안 그룹 | 서브넷 연결 시간과 접속 시간 과금 |

### Bastion + SSH 터널

퍼블릭 서브넷에 점프 서버를 두고 `ssh -L`로 터널을 엽니다. 구조가 단순하고 누구나 아는 방식이지만, 22번 포트를 열어야 하고 입퇴사 때마다 키를 배포하고 회수해야 합니다. 누가 언제 접속했는지 추적하려면 별도 작업이 필요합니다.

### SSM Session Manager 포트포워딩

SSM은 RDS에 직접 붙지 못합니다. RDS에는 SSM 에이전트를 설치할 수 없기 때문입니다. 그래서 에이전트가 도는 중계 EC2를 프라이빗 서브넷에 하나 두고, 그 인스턴스를 거쳐 RDS로 포워딩합니다.

```bash
aws ssm start-session \
  --target i-0123456789abcdef0 \
  --document-name AWS-StartPortForwardingSessionToRemoteHost \
  --parameters '{"host":["mydb.cluster-xxxx.ap-northeast-2.rds.amazonaws.com"],"portNumber":["3306"],"localPortNumber":["13306"]}'
```

에이전트가 바깥으로 연결을 맺는 방식이라 인바운드 규칙이 필요 없고, 권한은 IAM으로 관리되며, 세션 시작 기록이 CloudTrail에 남습니다. EKS가 없는 환경이라면 이 방식이 가장 무난한 선택입니다. 주의할 점은 이 SSM 문서가 `host` 파라미터에 임의의 주소를 받는다는 것입니다. 중계 EC2가 닿을 수 있는 모든 곳으로 터널이 열리므로, 범위를 좁히려면 호스트를 고정한 커스텀 문서를 만들어 그것만 허용해야 합니다.

### EC2 Instance Connect Endpoint

VPC 안에 엔드포인트를 만들어 퍼블릭 IP 없는 인스턴스에 SSH로 붙습니다. 에이전트가 필요 없다는 장점이 있지만 포트가 22와 3389로 제한되어 있어, RDS에 닿으려면 결국 EC2를 거쳐 SSH 터널을 한 번 더 열어야 합니다.

### kubectl port-forward

클러스터 안에 RDS로 트래픽을 넘겨 주는 프록시 파드를 띄우고, 로컬에서 그 파드로 포트포워딩합니다. EKS를 이미 운영 중이라면 새로 만들 것이 파드 하나뿐입니다. 아래에서 자세히 다룹니다.

### Client VPN

노트북을 VPC 네트워크에 직접 연결합니다. 터널을 따로 열 필요 없이 프라이빗 주소로 바로 접속할 수 있어 사용성은 가장 좋습니다. 반면 접근 범위가 넓어지므로 인가 규칙과 보안 그룹을 세밀하게 관리해야 하고, 사용 시간에 비례해 비용이 나옵니다.

## 우리 팀이 쓰는 방법

우리 환경에는 두 가지가 이미 있었습니다. EKS 클러스터, 그리고 SSO 로그인으로 AWS 임시 자격증명과 EKS 토큰을 받는 인증 체계입니다.

이 조건에서는 `kubectl port-forward`가 가장 적은 것을 추가하는 선택입니다. 중계 EC2도, VPN 엔드포인트도, 새로운 권한 체계도 필요 없습니다. 프록시 파드만 배포하면 기존 쿠버네티스 인증과 RBAC이 그대로 접근 통제 역할을 합니다.

DB가 아닌 서버 접속에는 SSM Session Manager를 씁니다. EC2에는 에이전트를 설치할 수 있으니 중계 노드 없이 바로 붙을 수 있어서입니다. 대상의 성격에 따라 방법을 나눠 쓰는 셈입니다.

## 구현

### 전체 경로

```text
로컬 클라이언트 (127.0.0.1:13306)
  └─ kubectl port-forward
       └─ EKS API 서버 (인증, 권한 확인)
            └─ socat 파드: TCP-LISTEN:3306 → TCP:mydb.example.com:3306
                 └─ Route53 CNAME
                      └─ RDS 클러스터 엔드포인트
```

### 프록시 파드가 필요한 이유

`kubectl port-forward`는 클러스터 안의 파드로만 포워딩할 수 있습니다. RDS처럼 클러스터 밖에 있는 주소로는 직접 갈 수 없습니다. 그래서 받은 TCP 연결을 RDS로 그대로 넘겨 주는 중계 파드가 필요합니다.

### socat으로 L4 중계

중계에는 socat을 씁니다. socat은 두 통신 지점을 양방향으로 이어 주는 명령줄 도구로, 설정 파일 없이 명령 한 줄로 TCP 중계를 만들 수 있습니다.

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: app-mysql-proxy
spec:
  serviceName: app-mysql-proxy
  replicas: 1
  selector:
    matchLabels:
      app: app-mysql-proxy
  template:
    metadata:
      labels:
        app: app-mysql-proxy
    spec:
      containers:
        - name: socat
          image: alpine/socat
          command:
            - socat
            - TCP-LISTEN:3306,fork,reuseaddr
            - TCP:mydb.example.com:3306
          ports:
            - containerPort: 3306
          resources:
            requests:
              cpu: 50m
              memory: 64Mi
            limits:
              cpu: 100m
              memory: 128Mi
          securityContext:
            allowPrivilegeEscalation: false
            capabilities:
              drop: ["ALL"]
              add: ["NET_BIND_SERVICE"]
---
apiVersion: v1
kind: Service
metadata:
  name: app-mysql-proxy
spec:
  type: ClusterIP
  selector:
    app: app-mysql-proxy
  ports:
    - port: 3306
      targetPort: 3306
```

`TCP-LISTEN:3306`은 파드의 3306 포트에서 연결을 기다리고, 연결이 들어오면 `TCP:mydb.example.com:3306`으로 새 연결을 맺어 둘을 이어 붙입니다. `fork`는 연결마다 자식 프로세스를 만들어 여러 사용자가 동시에 쓸 수 있게 합니다. 바이트만 옮기는 프로세스라 CPU 50m, 메모리 64Mi 요청으로 충분합니다.

우리는 StatefulSet으로 배포했지만 볼륨도 고정 식별자도 쓰지 않으므로, Deployment로 배포해도 똑같이 동작합니다.

socat은 지나가는 바이트를 해석하지 않습니다. TLS를 종료하지 않고, 인증에 관여하지 않고, 커넥션 풀링도 하지 않습니다. DB 로그인과 TLS 암호화는 클라이언트와 RDS 사이에서 그대로 이뤄지므로 프록시가 비밀번호나 쿼리 내용을 볼 일이 없습니다. 기능이 없는 만큼 운영할 것도 거의 없습니다.

RDS 쪽에서는 프록시 파드가 클라이언트로 보입니다. 따라서 RDS 보안 그룹은 파드의 트래픽이 나가는 출처(노드 보안 그룹, 또는 파드 단위 보안 그룹을 쓴다면 그 그룹)에서 오는 DB 포트를 허용해야 합니다.

### CNAME으로 엔드포인트 간접 참조

매니페스트에는 RDS 엔드포인트를 직접 적지 않고, 우리가 관리하는 도메인의 CNAME을 적습니다. 그 CNAME이 Route53에서 RDS 클러스터 엔드포인트를 가리킵니다. 이렇게 하면 DB가 바뀌어도 매니페스트를 건드리지 않고 DNS 레코드만 바꾸면 됩니다.

CNAME을 바꾸면 이미 맺어진 연결은 기존 DB에 그대로 남고, 새 연결은 DNS 캐시가 만료되는 약 1분 뒤부터 새 엔드포인트로 갑니다. socat이 연결마다 자식 프로세스에서 호스트명을 새로 조회하기 때문이며, 프록시 재시작은 필요 없습니다. 실제로 클론용 프록시는 몇 주째 재시작 없이 떠 있으면서 매일 바뀌는 클론을 따라가고 있습니다.

이 구조가 가장 잘 쓰이는 곳이 운영 DB의 클론입니다. 우리는 매일 자정 무렵 배치 작업으로 운영 DB의 클론을 새로 만들고 전날 클론은 삭제하며, 고정된 CNAME이 항상 그날의 클론을 가리키게 합니다. 개발자는 운영 DB 대신 클론에 접속해 무거운 조회나 검증 쿼리를 실행하고, 프록시와 접속 명령은 클론이 교체되어도 그대로입니다.

### ClusterIP만 쓰고 Ingress는 두지 않는다

프록시 Service는 전부 ClusterIP입니다. ClusterIP는 클러스터 내부에서만 통하는 가상 IP라 클러스터 밖에서는 라우팅되지 않습니다. DB용 Ingress나 LoadBalancer도 만들지 않았습니다.

그 결과 클러스터 밖에서 프록시에 닿는 경로는 `kubectl port-forward` 하나만 남습니다. 이 명령은 프록시에 직접 접속하지 않고 쿠버네티스 API 서버를 거쳐 파드까지 터널을 엽니다. 따라서 다음이 보장됩니다.

- 유효한 토큰이 있어야 합니다. SSO 로그인을 거치지 않으면 터널을 열 수 없습니다.
- RBAC에서 `pods/portforward` 권한이 있는 사용자만 쓸 수 있습니다.
- 네트워크를 스캔해도 DB 프록시 포트가 보이지 않습니다.

Service를 LoadBalancer로 만들었다면 주소를 아는 누구든 DB 로그인 단계까지 도달할 수 있고, 보안 그룹과 DB 비밀번호만이 방어선이 됩니다.

### 인증 흐름

```text
SSO 로그인 → AWS 임시 자격증명 → EKS 토큰 → kubectl port-forward
```

개발자에게 장기 자격증명을 나눠 주지 않습니다. 세션이 만료되면 다시 로그인해야 터널을 열 수 있고, 퇴사자는 SSO 계정이 비활성화되는 순간 접근이 끊깁니다.

## 한 줄 명령으로 포장하기

컨텍스트, 네임스페이스, 서비스 이름, 포트를 매번 입력하게 하면 아무도 쓰지 않습니다. 그래서 셸 스크립트로 감싼 사내 CLI를 만들었습니다.

```bash
devcli pf dev            # dev DB 터널 전체
devcli pf prd orders     # prd의 특정 DB만
devcli pf --status       # 떠 있는 터널 목록
devcli pf --stop         # 모든 터널 종료
```

내부는 환경과 대상 이름을 컨텍스트, 서비스, 포트로 바꿔 주는 매핑 표와 아래 한 줄이 전부입니다.

```bash
nohup kubectl --context="$ctx" -n "$ns" port-forward "svc/${svc}" "${lport}:${rport}" \
  </dev/null >"$logfile" 2>&1 &
echo $! >"$pidfile"
```

쓰면서 다듬은 부분은 이렇습니다.

- **백그라운드 터널**: 터미널에서 분리해 실행하고 pid 파일을 남겨, 터미널을 닫아도 터널이 유지되고 상태 확인과 종료가 됩니다.
- **고정 로컬 포트**: 환경별로 포트 대역을 나눠 dev와 prd를 헷갈리지 않게 했습니다.
- **로컬 전용 바인딩**: 터널은 127.0.0.1에만 열립니다.
- **사전 점검**: 포트가 이미 쓰이고 있거나 인증이 만료되었으면, 원인과 다음에 실행할 명령을 알려 주고 멈춥니다.

배포는 Homebrew tap으로 합니다. 설치는 `brew install`, 업데이트는 `brew upgrade`로 끝나고, 버전은 Git 태그로 고정합니다.

## 한계와 트레이드오프

**접근 통제 단위가 거칩니다.** 프록시가 있는 네임스페이스에서 port-forward 권한을 받으면 그 안의 모든 프록시에 닿을 수 있습니다. 파드 단위로 좁혀야 한다면 Role의 `resourceNames`에 허용할 파드 이름을 적는 방법이 있고, 이때는 파드 이름이 고정되는 StatefulSet이 유리합니다. 다만 `svc/이름`으로 포워딩하는 편의는 포기하고 파드 이름을 직접 지정해야 합니다. 어느 쪽이든 DB별 최종 통제는 DB 계정과 권한의 몫입니다.

**프록시가 단일 레플리카입니다.** 파드가 재시작되면 열려 있던 연결이 모두 끊깁니다. 개발자 접속용이라는 용도를 고려해 감수한 선택입니다.

**클러스터 내부 접근은 따로 막아야 합니다.** ClusterIP는 클러스터 밖에서의 접근만 차단합니다. 클러스터 안의 다른 파드는 프록시에 그대로 접속할 수 있으므로, 이를 제한하려면 NetworkPolicy가 필요합니다.

**터널 안은 기록되지 않습니다.** API 서버 감사 로그로 누가 언제 port-forward를 요청했는지는 알 수 있지만, 어떤 쿼리를 실행했는지는 알 수 없습니다. 쿼리 감사는 DB의 감사 로그로 해야 합니다.

**TLS 호스트명 검증이 맞지 않습니다.** 클라이언트는 127.0.0.1로 접속하는데 RDS 인증서는 RDS 엔드포인트 이름으로 발급되어 있습니다. 호스트명까지 검증하는 모드에서는 연결이 실패하므로, 검증 수준을 CA 확인까지로 맞추거나 hosts 파일로 엔드포인트 이름을 로컬에 매핑해야 합니다.

**상시 연결용이 아닙니다.** `kubectl port-forward`는 API 서버를 경유하고, 오래 유휴 상태면 끊기기도 합니다. 사람이 쓰는 임시 접속에는 충분하지만 애플리케이션의 상시 연결이나 대량 데이터 전송에는 맞지 않습니다.

## 상황별 추천

- **EKS를 이미 운영 중이다**: `kubectl port-forward` + 프록시 파드. 추가 리소스가 가장 적습니다.
- **EKS가 없다**: SSM 포트포워딩 + 프라이빗 중계 EC2. 인바운드 포트 없이 IAM으로 통제됩니다.
- **접근 대상이 많고 상시 접근이 필요하다**: Client VPN. 대신 인가 규칙을 세밀하게 관리해야 합니다.
- **Bastion + SSH**: 새로 만든다면 권하지 않습니다. 이미 쓰고 있다면 SSM으로 옮기는 것을 검토할 만합니다.

어떤 방법을 고르든 접속 경로는 네트워크 문제만 해결합니다. 누가 어떤 데이터를 볼 수 있는가는 DB 계정 권한, 감사 로그, 그리고 운영 DB 대신 쓸 수 있는 클론 같은 장치가 함께 있어야 답할 수 있습니다.
